# Decisions

## 2026-09-28: Phase 1 KB inspection

**Parse the normal article page, not the print page.**
The article body sits in one stable container on all 13 samples,
and Related Articles and the feedback widget are outside it. The
print page has the same body text but no meta tags, so category,
dates, and tags would be lost.

**Plain HTTP for collection, no browser automation.**
All 13 test sentences I copied from the browser were found in the
raw HTML, on both page versions. Category pages list every article
as a plain link with no pagination, so discovery is a recursive
walk of category pages.

**Strip tags without adding spaces for the server-rendered test.**
The first run failed one article because the script added a space
where it removed a link tag ("eAccounts , students"). That was a
bug in the test, not the site. Removing tags with no inserted space
passed 13/13.

**6-second delay between requests.**
robots.txt sets Crawl-delay: 5. I use 6 for margin. Phase 1 used
2 seconds for 28 requests before this was known.

## 2026-09-29: Phase 2 collection and parsing

**Collect all of Technology, not a subset.**
The recursive walk found 3,109 unique articles, about 2.5x the
estimate. All are indexed so search is tested against the real
candidate pool.

**Raw HTML stays local; parsed output and manifests are committed.**
Raw HTML is ~55 MB and can be regenerated. The parsed articles
(9.4 MB) and manifests are what later phases build on.

**Staff-only content is kept separate from searchable text.**
40% of articles have an "ITS STAFF ONLY" box or "Internal Staff
Only" panel. It goes into its own field so I can measure later
whether including it helps or hurts search.

**Department labels are not staff-only.**
"USD/HR/FINANCE/EPC STAFF ONLY" boxes describe who the content is
for, and some hold the whole answer (e.g. 10177's Resolution). I
record the label and keep the content searchable.

**Footers: remove only the standard contact line.**
I first assumed footers were boilerplate. Article 8721 showed real
content in its footer, so now only the standard service-desk line
is removed and everything else stays searchable.

**Flag instead of guess.**
When the parser can't identify a layout with a clear rule, it keeps
the text and raises a warning. The remaining warnings were reviewed
and accepted as known limitations.



## 2026-09-29: Phase 3 evaluation rules

Set before any queries are frozen, so they are not tuned to results.

**A positive with no fitting article becomes a negative.**
Queries are drafted with no KB access, so some will have no match in
the 3,109. If none fits, I set has_match to false and leave the
query text unchanged. I log how many flipped here.

**Several targets per case are allowed.**
The KB has near-duplicates (per-OS versions of one how-to). A hit is
any target ID in the top k.

**Negatives are report-only.**
Top article, top score, ranked list. No pass/fail and no threshold
until an abstention mechanism exists.

**Queries are frozen before targets are assigned.**
Two commits: queries first, then target IDs. No rewording after the
first one.

**Candidates for targets come from category browsing first.**
Keyword grep is second, and each candidate is recorded with how it
was found. This keeps targets from skewing toward lexical matches.

**Where the case topics came from.**
The first 25 scenario topics (accounts, Duo, Wi-Fi, Microsoft 365,
printing, D2L/myUSD/Respondus, 5 out-of-scope negatives) were
generated by ChatGPT from my project scope and workflow context, not
from browsing the KB or article titles. I cannot verify whether that
context included the Phase 1 sample articles, so topics naming D2L,
myUSD and Respondus may be easier than cold ones. The final set
also uses cases from drafts written without a topic list. Lexical
numbers should be read with that in mind.

**Labels can change only during 3b.**
If labeling finds no fitting article for a positive, or a real one for
a negative, has_match changes and the query text stays unchanged. I log
the count of changes here after 3b; git history has the per-case detail.
No label changes after the first eval run.

**Set size.**
20 positives and 5 negatives, as in WORKFLOW.md.

## 2026-09-30: Phase 4 lexical baseline configuration (frozen)

Set before any evaluation run. Nothing below changes after seeing
eval numbers. Any later change is a new, logged experiment.

**Retrieval.**
Postgres full-text search, called the "Postgres FTS baseline", not
BM25. english config. Search vector: title weight A, tags and
description weight B, full text weight C. staffOnly is stored but not
indexed or searchable. The vector is a stored generated column and
app code never computes it.

**Query handling.**
The query goes through the same english parser as the documents. The
distinct lexemes are ORed together, so long natural-language queries
still match. Empty, punctuation-only or stopword-only input gives no
results, returned as 200 with an empty list.

**Ranking.**
ts_rank with default weights and normalization 0. Ties break on
source_article_id with C collation. Ranking lives in one SQL
function, kb_search_lexical. /api/search calls it and nothing
reimplements it.

**Depth and metrics.**
Fixed retrieval depth of 50, not settable by the client. The UI shows
10. Reported per track: Top-1, Top-3, MRR@50 (a miss scores 0) and the
count of positives with no target in the top 50. Semantic retrieval
later uses the same depth of 50.

**What is pinned.**
Corpus: data/parsed/articles.jsonl, 3,109 articles, parserVersion 2,
sha256 103f2b008085d9e38ece49b3e67467ae527d6fea1b8c26935e507ab16da9c1d3.
Migration: supabase/migrations/20260930042716_create_articles.sql,
sha256 93903628588f6f313e33ebe130d6c0de8f0e17817602034c27289f46a7d02d59.

**How it was checked.**
Behavior was tested on placeholder articles in a throwaway schema.
No query or ranking was tried on the real corpus. The SQL needed no
changes after the first apply. Weak numbers are baseline evidence, not
a reason to retune.

## 2026-09-30: Phase 4 slice 2, search API (frozen with the baseline)

**Database settings.**
statement_timeout 5000 ms and a pool of 5 connections are part of the
frozen baseline. They do not change after seeing eval results.

**Request rules.**
Extra request fields are rejected with 400. An empty query string is
rejected with 400. Whitespace-only, punctuation-only and stopword-only
input returns 200 with an empty result list. Depth is fixed at 50 on
the server.

**Pinned versions.**
Next.js 16.3.8, React 19.2.8, TypeScript 5.9.3, ESLint 9.39.5, zod
4.6.5, pg 8.23.1, Vitest 5.0.3, all exact, with the lockfile
committed.

**Privacy checks.**
Query text is never logged, echoed, stored or put in a URL. A
sentinel test covers ten request paths, and the real-data tests only
check empty results and invalid requests, never rankings.

## 2026-10-01: Phase 5 semantic-v1 configuration and decision rule (frozen)

Set before the article embed and before any semantic eval run.
Nothing below changes after seeing semantic numbers. Any later
change is a new, logged experiment.

**Embedding.**
OpenAI text-embedding-3-small, dimensions 1536 passed on every call.
article-v1 is exactly "Title: {title}\n\n{fullText}" with LF. No
tags, description, category or staffOnly. Lexical indexes title,
tags, description and full text, so the two modes do not see
identical fields. Queries are embedded as typed (raw-query-string-v1).

**Truncation.**
cl100k_base via tiktoken==0.14.0 (identity is the encoding file
sha256 below, not the package version). First 8,000 tokens, sent as
token IDs only for articles over the limit. Chosen from corpus
counts only: max 15,775, p50 128, p95 408. One article is truncated
(9431). Encoding file sha256
223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7.

**Ranking.**
Exact cosine search with pgvector, no ANN index. Score is 1 minus
cosine distance (cosine similarity, not a probability). Order is
score descending, then source_article_id COLLATE "C". Ranking lives

fail loudly on a bad k, unknown config, bad query vector, incomplete
embeddings or stale article text. The staleness check runs per
request (about 47 ms); revisit in Phase 7.

**Query privacy.**
Query embeddings are ephemeral. Query text, hash and vector are
never written anywhere. This supersedes the query cache in SPEC.md
and WORKFLOW.md.

## 2026-10-04: Phase 7 hosting decisions

**D1: No lexical fallback.**
A semantic failure (OpenAI error, missing key, KBF error, config
mismatch) returns 500 {"error":"Search failed"}. The daily cap returns
429. The server never retries a request in lexical mode, so a result
list always comes from the mode that was asked for.

**D2 (revised): Shared password gate.**
One shared password of at least 20 characters (ACCESS_PASSWORD), and a
cookie secret of at least 32 bytes (GATE_COOKIE_SECRET). POST /api/gate
sets kbf_gate=v1.<exp>.<mac>, where the MAC is
HMAC-SHA256(secret, "kbf_gate|v1|" + exp + "|" + sha256hex(password)).
Because the password hash is in the MAC, rotating either the secret or
the password revokes every issued cookie. HttpOnly, Secure,
SameSite=Lax (not Strict, so links from email or LinkedIn work), 7
days. No login rate limit, so the hosted password is generated, not
chosen. A missing or short password or secret fails closed.
ACCESS_GATE=off works only when VERCEL is unset.

**Proxy excludes /api/search.**
In Next 16, a proxy that matches a request buffers its body (10 MB by
default, silently truncated above that). proxy.ts therefore excludes
/api/search and /api/gate, and /api/search checks the gate cookie
itself before reading the body. The proxy only redirects page
requests.

**Scope change: one global daily cap (replaces D3, drops D4).**
The hosted app is for the project owner plus at most 2-3 trusted
testers. D3 (global cap of 1,000/day) is replaced by a cap of 200 valid,
allowed searches per UTC day across both modes; search 201 gets 429.
D4 (per-IP limits, revised to 60 per 10 min and 300/day) is dropped,
along with the client IP header and its HMAC secret. Deviation from the
approved plan, which counted every request before the body was read:
now 401, 400 and 413 responses do not count, and a valid search that
fails after the cap check does. RATE_LIMIT=off works only when VERCEL
is unset.

**D5: KBF02 server-side check.**
kb_search_semantic raises KBF02 only when no embedding_configs row
exists for the config sha256. Before embedding the query, the server
also requires exactly one row whose config (canonical JSON), model,
dimensions and template_version equal config/embedding/article-v1.json.
A mismatch is 500 and spends no OpenAI call. Only a pass is cached, per
server process. Chosen over a CHECK constraint, which would have broken
the config '{}' test fixture. No database constraint binds
config_sha256 to config.

**D6: S1, search_path pinned with transaction-local set and restore.**
ALTER FUNCTION ... SET search_path FROM CURRENT on the five kb_
functions, with the path set transaction-locally to the session's
existing schemas plus pg_temp, then restored. Bodies (prosrc) and
ranking are unchanged, proven by before/after tests on exact score
text as postgres and as kb_app. After db push, check on hosted that
all five show search_path=public, extensions, pg_temp.

**D7 (revised): UI pass moved to step 16.**
After deploy and the hosted checks, time-boxed to 1-2 days. Visual
only: no change to the API, ranking, gate, cap or privacy rules. Mobile
first. Tailwind pinned to an exact version; shadcn only if a component
needs it. Example queries, if any, are new and never taken from
eval/cases.json. Phase 7 code only switched the UI to the server
default mode and added fixed error messages.

**App role kb_app and the statement timeout.**
The app connects as kb_app (no superuser, createdb, createrole or
bypassrls): SELECT on the three KB tables, EXECUTE on the four
functions the searches call, write access only to kb_rate_counters.
statement_timeout 5000 ms is set on the role, because the pool's
startup option may not survive a transaction pooler. Verified by hand
through the local pooler as kb_app: statement_timeout 5s, pg_sleep(6)
fails with 57014. The login password is set by hand as a SCRAM
verifier and is in no file.

**D8: auto_explain invariant (A1 done, A2 not attempted).**
Locally, auto_explain.log_min_duration is 10000 ms and
log_parameter_max_length is -1, so a statement over 10 s would be
logged with its bind parameters (query text). statement_timeout 5000 ms
on kb_app keeps every app statement below that. Any change must keep
statement_timeout below log_min_duration. A2 (setting
log_parameter_max_length = 0 on kb_app) was planned as "try" and not
attempted. Decide at deploy after reading the hosted values with
db_fingerprint.py --settings; hosted values are unverified.

**D9: Manual pause check.**
The Supabase free tier pauses after 7 idle days. The project owner
checks it by hand before demos; no keep-alive job.

**D10: RLS policies for kb_app.**
RLS stays on for every table. RLS with no policies would block kb_app
too, so the only policies are for kb_app: SELECT on articles,
embedding_configs and article_embeddings, and ALL on kb_rate_counters.
anon, authenticated and PUBLIC have no privileges and no policies.

**D11: Restricted, Vercel-only OpenAI key.**
The hosted app uses its own restricted key in the dedicated KB Finder
OpenAI project, set only as a server-side Vercel environment variable,
Production only, marked Sensitive, never in a file. Agents never set or
read it. OpenAI-side controls set by hand: embeddings-only key
permissions, model allow-list text-embedding-3-small, project rate
limits, low prepaid credit, auto-reload off, budget alert. It can be
revoked without touching the eval key.

**D12: Local transaction pooler.**
supabase/config.toml enables [db.pooler] on 54329 so the hosted path
(kb_app through a transaction pooler, unnamed statements) is tested
locally. Scripts, tests and local dev stay on the direct port 54322.

**service_role grants left as Supabase sets them.**
The lockdown migration revokes from anon, authenticated and PUBLIC
only. The app never uses the service key, and the Data API is disabled
on hosted.

**Global default-privilege revoke.**
ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON ROUTINES
FROM PUBLIC applies globally, not per schema, because per-schema
defaults can only add to the global ones. Future functions created by
postgres, in any schema, get no PUBLIC EXECUTE.

**Unused per-IP kinds kept in the kb_rate_counters CHECK.**
search_ip_10m, search_ip_day and gate_ip_10m (64-hex keys) stay allowed
so per-IP limits can return without a table change. The app uses only
search_global_day with key 'all'; no IP or IP hash is stored.

**Hosted TLS rules.**
When VERCEL is set, DATABASE_CA_PEM (the Supabase database CA, real
multi-line PEM) is required and the server verifies the chain and the
hostname. DATABASE_URL must have no query string, because in pg 8.23.1
URL parameters replace the ssl object (sslmode=require would drop the
CA, and statement_timeout=0 would disable the timeout). A certificate
error at deploy is fixed by a reviewed CA change, never by sslmode or
turning verification off.

vectors_sha256 921b8f5659e8f09c3f458fe9722c44a8386ecbb9b857846c7b829163eb4aedd0
Captured from the local database with scripts/db_fingerprint.py. The

## 2026-10-04: D2 revised again: 4-digit PIN with a failed-login cap

The hosted app is a low-value private tool: all KB content is public, the
only spend is bounded by the 200/day search cap and a small prepaid OpenAI
balance, and no secret or write access sits behind the gate. A 4-digit PIN
is easy to share in person and type on any device, so ACCESS_PASSWORD may
now be exactly 4 ASCII digits, or still a passphrase of at least 20
characters. Anything else fails closed. Cookie format, MAC (with
sha256 of the password), flags and the 7-day lifetime are unchanged.

Brute force is bounded by a global cap of 10 failed logins per UTC day
(GATE_FAIL_CAP), not by password length. Each attempt atomically reserves
a slot in kb_rate_counters (kind gate_fail_global_day, key 'all') BEFORE
the PIN is compared; a correct PIN releases its slot. Attempt 11 of a day
gets 429 and the PIN is never compared. Check-then-count was rejected
because concurrent guesses could bypass it. A release error after a
correct PIN still logs the user in; the attempt stays counted.

Expected time to guess a 4-digit PIN at 10 tries a day is about 1.4
years (about a 3% chance within a month). Accepted tradeoff: anyone can
lock out NEW logins until the next UTC day by failing 10 times; devices
already logged in keep working. Per-device or per-IP limits were rejected
as the primary control, because a client controls its cookie and IP.
Rotate the PIN after AfroTech.

Migration 20261004232626_add_gate_fail_kind.sql replaces the two CHECK
constraints on kb_rate_counters to allow the new kind; no grant changes.
