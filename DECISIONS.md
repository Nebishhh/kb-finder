# Decisions

## 2026-09-28: Phase 1 KB inspection

**Parse the normal article page, not the print page.**
The article body sits in one stable container on all 13 samples,
and Related Articles and the feedback widget are outside it. The
print page has the same body text but no meta tags, so category,
dates, and tags would be lost.

**Plain HTTP for collection, no browser automation.**
All 13 test sentences I copied from the browser were found in the
raw HTML, on both page versions. Category pages list every article
as a plain link with no pagination, so discovery is a recursive
walk of category pages.

**Strip tags without adding spaces for the server-rendered test.**
The first run failed one article because the script added a space
where it removed a link tag ("eAccounts , students"). That was a
bug in the test, not the site. Removing tags with no inserted space
passed 13/13.

**6-second delay between requests.**
robots.txt sets Crawl-delay: 5. I use 6 for margin. Phase 1 used
2 seconds for 28 requests before this was known.

## 2026-09-29: Phase 2 collection and parsing

**Collect all of Technology, not a subset.**
The recursive walk found 3,109 unique articles, about 2.5x the
estimate. All are indexed so search is tested against the real
candidate pool.

**Raw HTML stays local; parsed output and manifests are committed.**
Raw HTML is ~55 MB and can be regenerated. The parsed articles
(9.4 MB) and manifests are what later phases build on.

**Staff-only content is kept separate from searchable text.**
40% of articles have an "ITS STAFF ONLY" box or "Internal Staff
Only" panel. It goes into its own field so I can measure later
whether including it helps or hurts search.

**Department labels are not staff-only.**
"USD/HR/FINANCE/EPC STAFF ONLY" boxes describe who the content is
for, and some hold the whole answer (e.g. 10177's Resolution). I
record the label and keep the content searchable.

**Footers: remove only the standard contact line.**
I first assumed footers were boilerplate. Article 8721 showed real
content in its footer, so now only the standard service-desk line
is removed and everything else stays searchable.

**Flag instead of guess.**
When the parser can't identify a layout with a clear rule, it keeps
the text and raises a warning. The remaining warnings were reviewed
and accepted as known limitations.



## 2026-09-29: Phase 3 evaluation rules

Set before any queries are frozen, so they are not tuned to results.

**A positive with no fitting article becomes a negative.**
Queries are drafted with no KB access, so some will have no match in
the 3,109. If none fits, I set has_match to false and leave the
query text unchanged. I log how many flipped here.

**Several targets per case are allowed.**
The KB has near-duplicates (per-OS versions of one how-to). A hit is
any target ID in the top k.

**Negatives are report-only.**
Top article, top score, ranked list. No pass/fail and no threshold
until an abstention mechanism exists.

**Queries are frozen before targets are assigned.**
Two commits: queries first, then target IDs. No rewording after the
first one.

**Candidates for targets come from category browsing first.**
Keyword grep is second, and each candidate is recorded with how it
was found. This keeps targets from skewing toward lexical matches.

**Where the case topics came from.**
The first 25 scenario topics (accounts, Duo, Wi-Fi, Microsoft 365,
printing, D2L/myUSD/Respondus, 5 out-of-scope negatives) were
generated by ChatGPT from my project scope and workflow context, not
from browsing the KB or article titles. I cannot verify whether that
context included the Phase 1 sample articles, so topics naming D2L,
myUSD and Respondus may be easier than cold ones. The final set
also uses cases from drafts written without a topic list. Lexical
numbers should be read with that in mind.

**Labels can change only during 3b.**
If labeling finds no fitting article for a positive, or a real one for
a negative, has_match changes and the query text stays unchanged. I log
the count of changes here after 3b; git history has the per-case detail.
No label changes after the first eval run.

**Set size.**
20 positives and 5 negatives, as in WORKFLOW.md.

## 2026-09-29: Phase 3b target assignment

**Label changes: 3, query text unchanged.**
case_013 (charged for a print that never printed) became has_match
false: the only student-facing refund article never mentions printing
and the print-funds fix is staff-only. case_021 (broken personal
laptop) and case_023 (slow home internet) became has_match true after
finding articles that answer them. The set is 21 positives and 4
negatives, not 20 and 5. case_005 stayed a positive as a judgment
call: the generic wifi articles fix it even though they never
mention a password change. case_025 stayed a negative: the nearest
articles cover USB printers and campus wireless, not a home Wi-Fi
printer.

**Targets.**
8 positives have two targets (002, 004, 005, 007, 010, 014, 016,
018) and 13 have one. Candidates came from category browsing with
no keyword search. Per the agent's flags, every target has its
answer in student-facing text. case_009 and case_018 are partial
matches: no article names the exact symptom.

**Rule used for targets.**
An article is a target only if following it would resolve the issue
as the case is written. Multiple targets are included only when each
article is a legitimate answer on its own, such as near-duplicates or
articles for different platforms the case does not rule out.
Adjacent or background articles and articles that answer only part of
the case are not targets, because any target counts as a hit.

## 2026-09-30: Phase 4 lexical baseline configuration (frozen)

Set before any evaluation run. Nothing below changes after seeing
eval numbers. Any later change is a new, logged experiment.

**Retrieval.**
Postgres full-text search, called the "Postgres FTS baseline", not
BM25. english config. Search vector: title weight A, tags and
description weight B, full text weight C. staffOnly is stored but not
indexed or searchable. The vector is a stored generated column and
app code never computes it.

**Query handling.**
The query goes through the same english parser as the documents. The
distinct lexemes are ORed together, so long natural-language queries
still match. Empty, punctuation-only or stopword-only input gives no
results, returned as 200 with an empty list.

**Ranking.**
ts_rank with default weights and normalization 0. Ties break on
source_article_id with C collation. Ranking lives in one SQL
function, kb_search_lexical. /api/search calls it and nothing
reimplements it.

**Depth and metrics.**
Fixed retrieval depth of 50, not settable by the client. The UI shows
10. Reported per track: Top-1, Top-3, MRR@50 (a miss scores 0) and the
count of positives with no target in the top 50. Semantic retrieval
later uses the same depth of 50.

**What is pinned.**
Corpus: data/parsed/articles.jsonl, 3,109 articles, parserVersion 2,
sha256 103f2b008085d9e38ece49b3e67467ae527d6fea1b8c26935e507ab16da9c1d3.
Migration: supabase/migrations/20260930042716_create_articles.sql,
sha256 93903628588f6f313e33ebe130d6c0de8f0e17817602034c27289f46a7d02d59.

**How it was checked.**
Behavior was tested on placeholder articles in a throwaway schema.
No query or ranking was tried on the real corpus. The SQL needed no
changes after the first apply. Weak numbers are baseline evidence, not
a reason to retune.

## 2026-09-30: Phase 4 slice 2, search API (frozen with the baseline)

**Database settings.**
statement_timeout 5000 ms and a pool of 5 connections are part of the
frozen baseline. They do not change after seeing eval results.

**Request rules.**
Extra request fields are rejected with 400. An empty query string is
rejected with 400. Whitespace-only, punctuation-only and stopword-only
input returns 200 with an empty result list. Depth is fixed at 50 on
the server.

**Pinned versions.**
Next.js 16.3.8, React 19.2.8, TypeScript 5.9.3, ESLint 9.39.5, zod
4.6.5, pg 8.23.1, Vitest 5.0.3, all exact, with the lockfile
committed.

**Privacy checks.**
Query text is never logged, echoed, stored or put in a URL. A
sentinel test covers ten request paths, and the real-data tests only
check empty results and invalid requests, never rankings.

Track B (technician_query), 21 positives: Top-1 8/21 (38%), Top-3

**Observations, not actions.**
The target is in the top 50 for 20 of 21 cases on both tracks, but is
first only about a third of the time. Both tracks are within one or
two cases of each other, which is not a difference at this sample
size. case_021 misses on both tracks (vocabulary gap: the query says

and case_025 returned articles close to what the student asked for,
which matters for the labels; per the Phase 3 rule labels do not change
after this run, so this goes to a later, separately versioned eval set.

**No tuning.**
Nothing in the lexical configuration, depth or labels changes because
of these numbers. Improvements are separate logged experiments, scored
at the same depth of 50.




## 2026-10-01: Phase 5 semantic-v1 configuration and decision rule (frozen)

Set before the article embed and before any semantic eval run.
Nothing below changes after seeing semantic numbers. Any later
change is a new, logged experiment.

**Embedding.**
OpenAI text-embedding-3-small, dimensions 1536 passed on every call.
article-v1 is exactly "Title: {title}\n\n{fullText}" with LF. No
tags, description, category or staffOnly. Lexical indexes title,
tags, description and full text, so the two modes do not see
identical fields. Queries are embedded as typed (raw-query-string-v1).

**Truncation.**
cl100k_base via tiktoken==0.14.0 (identity is the encoding file
sha256 below, not the package version). First 8,000 tokens, sent as
token IDs only for articles over the limit. Chosen from corpus
counts only: max 15,775, p50 128, p95 408. One article is truncated
(9431). Encoding file sha256
223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7.

**Ranking.**
Exact cosine search with pgvector, no ANN index. Score is 1 minus
cosine distance (cosine similarity, not a probability). Order is
score descending, then source_article_id COLLATE "C". Ranking lives
only in kb_search_semantic. Depth 50. KBF01-05 make the function
fail loudly on a bad k, unknown config, bad query vector, incomplete
embeddings or stale article text. The staleness check runs per
request (about 47 ms); revisit in Phase 7.

**Query privacy.**
Query embeddings are ephemeral. Query text, hash and vector are
never written anywhere. This supersedes the query cache in SPEC.md
and WORKFLOW.md.

**What is pinned.**
Config config/embedding/article-v1.json, sha256
051e13da32f484a11e0e87188a71de984563e93a5b3e1495db6da4cd0cb99940.
Migration supabase/migrations/20261001011735_add_semantic_embeddings.sql,
sha256 ba47934f0a9365e975febc6bbb5c4e10a5b6307b8f1646424ec14d49836645fc.
Corpus unchanged, sha256
103f2b008085d9e38ece49b3e67467ae527d6fea1b8c26935e507ab16da9c1d3.
Preflight: 544,549 tokens to embed in 32 requests, projected
$0.011. The article cache sha256 is added here after the paid run.

**Decision rule.**
Same frozen cases and labels, same run_eval.py, depth 50. Semantic
becomes the default only if aggregate Track A Top-3 >= 16/21 AND
aggregate Track B Top-3 >= 11/21. These are aggregate counts, not
per-case. The scored run is the first complete real semantic eval.
Aborted runs do not count and are noted here. The fake-case smoke
run is not an eval run.

runs, planned equal to billed on every request, about $0.011. Nothing
